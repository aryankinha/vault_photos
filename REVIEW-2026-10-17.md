# Review of the current VaultPhotos changes

Reviewed on 17 October 2026. Scope: the uncommitted tracked changes and new source/test files relative to `3c66d0c`, with surrounding code inspected for integration. This is a review, not an implementation pass. Application source was not changed and nothing was deployed.

## Verdict

Do not release the current changes yet. Automated checks pass, but the viewer has two reproducible integration failures, prefetch can freeze the page, and the advertised rollback protection is not connected to the app.

## Findings

1. **P1 — Older media breaks on an empty OPFS cache.** `src/services/viewerService.js:82` takes the nullable result of `getCachedFile()` and unconditionally creates a Blob. A normal cache miss becomes a four-byte `null` Blob, and the network download never happens. Reproduced in Chromium: OPFS supported, zero backend fetches, returned Blob text `null`. Restore a cache-hit check and fall through to the network on null. Test an old non-chunked image and video with cleared browser storage.

2. **P1 — Prefetch can synchronously freeze the UI.** `src/hooks/usePrefetch.js:77` loops until the cache has fewer than eight entries, but `evictLRU()` skips every unresolved/queued entry. Hovering nine distinct photos before the first download completes leaves no evictable entry and the loop never progresses. Verified with the actual module logic, unresolved downloads, and an instrumented iteration guard. Make eviction return whether it removed an entry; defer/skip the new prefetch when it cannot make progress. Also pass cancellation through the actual download and prevent completed requests from repopulating the cache after lock/cancel.

3. **P1 — New chunked media fails in the full-file fallback.** `src/services/viewerService.js:51` creates `fileContext(id)` and passes it into `decryptFileChunks()`, which requires a chunk context. Reproduced with valid encrypted bytes and their correct digest: `Chunk crypto context kind must be 'chunk', got 'file'`. This affects new large images and new videos when service-worker streaming is unavailable. Use a base chunk context such as `{ kind: 'chunk', id }`, allowing each iteration to supply its index. Test multiple chunks, not only index zero.

4. **P2 — Rollback detection is unused, and uploads do not increment the revision.** `src/session/revision.js` and `src/crypto/rollback.js` have no production callers. Unlock and manifest loads never check a high-water mark. `src/services/uploadService.js:927` appends entries without increasing `manifest.revision`; deletion does increment it. Therefore earlier legitimate manifests can be accepted without the promised warning, even on returning devices. Wire scope setup/check/clear into the session lifecycle, cover cached manifest reads, and increment the revision for every metadata publication. Test the integrated flow, including two successive upload revisions and reopening the older one.

## How to run and inspect locally

Use a disposable private HF Dataset for testing. The local Worker still writes to the real Dataset named by `HF_REPO`.

1. Install the locked dependencies with `npm ci` if needed.
2. Copy `.dev.vars.example` to `.dev.vars` only if the destination does not already exist. Fill in `HF_TOKEN` and `HF_REPO`. Keep the provided loopback development mode and allowed origins.
3. Ensure `.env.local` contains `VITE_WORKER_URL=http://127.0.0.1:8787`. Your current local file already targets loopback.
4. In one terminal, run `npm run worker:dev`.
5. In another, run `npm run dev`, then visit the URL Vite prints, normally `http://localhost:5173`. If it chooses a different port, add that exact frontend origin to `.dev.vars` and restart the Worker.
6. Run `npm test`, `npm run lint`, `npm run build`, and `npm audit` after fixes.

Browser harnesses while Vite runs:

- Open `/tests/browser/cryptoWorkerHarness.html`; it runs automatically and should report `passed: true`.
- Open `/tests/browser/uploadIntegrationHarness.html`; in the browser developer console run `await runUploadIntegration()`. This uses an in-memory network double and does not write to HF.
- For streaming, first run `node tests/browser/streamFixtures.js`, open `/tests/browser/streamIntegrationHarness.html`, and run `await runStreamIntegration()` in the console. Afterwards run `node tests/browser/streamFixtures.js --clean`. Do not deploy generated fixtures.

## Manual acceptance checklist after fixes

- Create a test vault; lock it; reject a wrong passphrase; unlock using the correct passphrase.
- Upload JPEG/PNG files, a small video, an image over 50 MiB, and a video spanning several 8 MiB chunks. Refresh and verify every item remains visible and opens.
- Test an older existing vault in a fresh browser profile, with no local media cache. This exercises the legacy formats.
- Scroll through more than 50 thumbnails and test All / Photos / Videos. Hover rapidly over at least nine uncached photos with network throttling enabled; the page must remain responsive.
- Play videos; seek near the beginning, middle, and end. Repeat on an actual iPhone/Safari and Android/Chrome.
- Interrupt an upload by going offline, refreshing, or locking. After unlock, confirm it appears paused. Resume with the same original file; reject a different file; verify no duplicate entry. Test Cancel and Discard separately.
- In two tabs/devices, upload concurrently and upload while deleting. Confirm both valid changes survive, or a clear retryable conflict is shown.
- Delete a test image and chunked video. Refresh to confirm removal. Repository history and old encrypted objects may retain copies.
- Enable “Clear thumb cache on lock”, lock, and inspect browser storage. Verify previews are removed and full-resolution cached bytes remain encrypted.
- In staging, open browser Network tools: successful allowed-origin preflights, authenticated reads/writes, and rejection of unauthenticated writes. Check Worker logs for failures.

## Deployment changes required

### Frontend

Your `.env.local` overrides `.env` during a normal local production build. I verified that the generated HTML CSP and JavaScript currently contain the loopback backend. **Do not upload this `dist/` output.**

On Vercel, configure these build environment variables and rebuild:

```text
VITE_WORKER_URL=https://YOUR-PRODUCTION-WORKER-HOST
VITE_ACCESS_CREDENTIALS=include
```

For a local production build, explicitly supply the production Worker URL:

```sh
VITE_WORKER_URL=https://YOUR-PRODUCTION-WORKER-HOST VITE_ACCESS_CREDENTIALS=include npm run build
```

Use Vite framework settings, build command `npm run build`, and output directory `dist`. Keep `vercel.json` for route refresh support and security headers. Rebuild whenever the Worker origin changes because the CSP includes it. Commit the new source files, security module, and icons alongside the modified tracked files so a clean deployment has all imports/assets.

### Cloudflare Worker

Supply these production values through Worker variables/secrets (the checked-in config currently contains comments, not actual values):

| Setting | Value |
| --- | --- |
| `HF_TOKEN` | HF token with write permission for the chosen Dataset; Worker secret only |
| `HF_REPO` | Exact `owner/dataset` identifier |
| `ALLOWED_ORIGIN` | Exact production frontend origin, plus any explicitly supported staging origins; comma separated, no trailing slash |
| `ACCESS_TEAM_DOMAIN` | `https://YOUR-TEAM.cloudflareaccess.com` |
| `ACCESS_AUD` | Audience tag of the Access application protecting the Worker |
| `ACCESS_EMAILS` | Optional additional identity email allowlist |

Configure an identity-based Cloudflare Access application/policy in front of the Worker and cover the actual hostname the frontend calls. Protect or disable alternate public Worker/preview hostnames. The code validates Access assertions itself; merely setting CORS origins does not satisfy authentication. Missing Access configuration makes production reads and writes fail closed.

Allow unauthenticated OPTIONS preflights through the gateway to the Worker's CORS handler, or configure equivalent preflight responses at Access. Complete Access login by visiting the Worker domain in the browser, then refresh the frontend. Same-site custom domains reduce cross-site-cookie problems. See [Cloudflare's CORS instructions](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/cors/).

Deploy the Worker before the rebuilt client, then run the staging checklist against the disposable Dataset. Open older client tabs may need a refresh because legacy write endpoints now return 410. Follow `DEPLOYMENT-SAFETY.md` for backup/recovery precautions. No encryption migration or replacement salt is required for existing vaults.
